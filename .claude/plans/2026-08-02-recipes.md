# Rezepte — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Nutzer legen eigene Rezepte an (Name, Portionen, Zutaten, Zubereitung), sehen sie in einer Sammlung, bearbeiten und löschen sie — und teilen sie **exakt wie Listen** (Besitzer lädt ein, Mitglieder sehen und ändern).

**Architecture:** Rezepte sind ein eigenes Aggregat (`RECIPE#{recipeId}`), das dieselbe Maschinerie benutzt wie Listen: Klasse-2-Command zum Erstellen (claimt Ownership), Klasse-1-Events für alles Weitere, dieselbe Membership-Projektion, dieselben Invite-/Join-/Member-Endpunkte. Das Teilen wird **generalisiert statt dupliziert**: Use Cases arbeiten künftig auf `AggregateId` statt auf `list_id`. Frontend: neuer `recipes`-Slice (`synced: true`), Sammlung/Detail/Formular nach den vorhandenen Mockups, Sharing-Screens wiederverwendet.

**Tech Stack:** Rust (lambda_http, aws-sdk-dynamodb), CDK (cargo-lambda-cdk), React + TanStack Router + eigener Redux-createSlice, Tailwind v4 + shadcn-Primitives, Vitest.

**Grundlage:** [`architecture/sharing-model.md`](../../architecture/sharing-model.md) — ein Mechanismus für Liste, Rezept und Plan. Mockups: `apps/mobile/design/pure/recipe-workflow/{recipes,recipe,new-recipe}.html`.

**Review eingearbeitet (2026-08-02):** Ein Plan-Review gegen den Code fand sechs Lücken (u.a. fehlendes `GET /recipes`, fehlende Recipe-Sharing-Routen, listen-hartkodierte Member-Events, fehlendes `createdBy`, Preferences, Join-Flow). Alle sind unten eingearbeitet. **Greenfield-Freigabe:** Es ist nichts live, kein Gerät hat Bestandszustand — persistierte Formate (Cursor-Schlüssel, Outbox) und API-Responses werden ohne Migration und ohne Abwärtskompatibilität sauber umgestellt.

## Entschieden: generalisieren, Tests werden mitgezogen

**Der User hat am 2026-08-02 ausdrücklich freigegeben**, das Teilen und den
Sync-Fan-out zu generalisieren und die dabei brechenden Bestandstests
anzupassen. Begründung: Nach den Rezepten kommt der **Wochenplan**, der genauso
geteilt wird. Zweimal duplizieren wäre einmal zu viel — beim dritten Aggregat
zahlt sich die Generalisierung endgültig aus.

Damit ist die Test-Policy für die unten genannten Dateien **erfüllt**; für
Tests, die hier *nicht* aufgeführt sind, gilt sie unverändert weiter.

### Was generalisiert wird — Backend

Die Sharing-Use-Cases nehmen heute eine `list_id` und bauen daraus intern
`AggregateId::list(...)`. Künftig nehmen sie eine fertige **`AggregateId`**:

| Use Case | heute | künftig |
|---|---|---|
| `create_invite` | `list_id: String` | `aggregate: AggregateId` |
| `join_list` → `join_aggregate` | `list_id` aus dem Token | `AggregateId` aus dem Token (steht dort schon) |
| `add_member` | `list_id: String` | `aggregate: AggregateId` |
| `remove_member` | `list_id: String` | `aggregate: AggregateId` |

Die Lambdas lesen den Aggregat-Typ aus dem Pfad — `/lists/…` bzw. `/recipes/…`
— und bauen die `AggregateId`. Ein Lambda bedient beide Routen; es gibt **keine**
`create-recipe-invite`-Lambda. Ausnahme Join: Dort kommt die `AggregateId` aus
dem Token, die Route bleibt `POST /lists/join` für alle Aggregate.

**Nicht alles ist mechanisch — die Member-Events sind heute listen-hartkodiert.**
`join_list`, `add_member` und `remove_member` schreiben fest
`lists/listMemberAdded` / `lists/listMemberRemoved` mit Payload-Key `listId`
(`join_list.rs:9`). Bei einem Rezept-Join würde ein Listen-Event mit einer
Rezept-ID im Log landen und clientseitig ins falsche Slice falten. Die
Generalisierung wählt Event-Typ und Payload-Key deshalb **kind-abhängig**:

| Kind | member added | member removed | Payload-Key |
|---|---|---|---|
| List | `lists/listMemberAdded` | `lists/listMemberRemoved` | `listId` |
| Recipe | `recipes/recipeMemberAdded` | `recipes/recipeMemberRemoved` | `recipeId` |
| Plan | `plans/planMemberAdded` | `plans/planMemberRemoved` | `planId` |

Die Zuordnung lebt **einmal** im Domain-Crate (z.B. als Methoden auf
`AggregateId`: `member_added_event()`, `member_removed_event()`,
`payload_id_field()`) — nicht verstreut über die drei Use Cases. Ein
Envelope-Schema brauchen diese Typen nicht: Sie sind server-geschrieben und
laufen wie heute an `validate_envelope` vorbei; die Allowlist lehnt sie am
generischen Pfad weiterhin ab.

**Die CDK-Routen fürs Rezept-Teilen gehören zu Task A** — Task 9 ist danach
reine Oberfläche:

```
POST    /recipes/{recipeId}/invites              → create-invite  (Kind aus Pfad)
POST    /recipes/{recipeId}/members              → add-member     (Kind aus Pfad)
DELETE  /recipes/{recipeId}/members/{memberId}   → remove-member  (Kind aus Pfad)
POST    /lists/join                              → join           (Kind aus Token, Route bleibt)
```

**Betroffene Testdateien** (Aufrufe bekommen eine `AggregateId` statt eines
Strings, Bedeutung unverändert):

- `services/domain/src/usecases/create_invite.rs` — 5 Tests
- `services/domain/src/usecases/join_list.rs` — 7 Tests
- `services/domain/src/usecases/add_member.rs` — 7 Tests
- `services/domain/src/usecases/remove_member.rs` — 5 Tests

⚠️ **Die Signatur-Umstellung ist rein mechanisch** — alle bestehenden
Assertions (inklusive `lists/listMemberAdded` als Event-Typ) bleiben wörtlich
stehen. Ändert ein Bestandstest seine *Aussage*, ist das ein Fehler im Umbau —
dann stoppen und nachfragen, nicht die Erwartung anpassen. Das kind-abhängige
Event-Schreiben ist dagegen **neues Verhalten** und bekommt **neue** Tests
(Recipe-Join schreibt `recipes/recipeMemberAdded` mit `recipeId`), keine
geänderten.

### Was generalisiert wird — Sync

`catchUp` kennt heute nur Listen. Künftig zieht es alle Aggregate, die der
Nutzer sehen darf:

| Baustein | heute | künftig |
|---|---|---|
| `fetchListIds()` | `readonly string[]` | `fetchAggregates()` → `{ kind, id }[]` |
| `eventsPathFor(id)` | `/lists/{id}/events` | `eventsPathFor(kind, id)` |
| `aggregates_of` (Rust) | filtert `LIST#` weg | liefert alle Kinds mit Typ |
| `GET /lists` | nur Listen | bleibt; dazu `GET /recipes` nach demselben Muster |

**`GET /recipes` ist ein voller Bestandteil von Task B, keine Randnotiz.**
Ohne den Endpunkt kann `fetchAggregates()` keine Rezept-IDs liefern — ein
frisches oder frisch beigetretenes Gerät fände nie ein Rezept. Das
`get-lists`-Lambda bedient beide Routen (Kind aus dem Pfad, wie in Task A):
`GET /recipes` antwortet `{ recipes: [ids], ownerNames, maxMembers }` — dasselbe
Muster wie `GET /lists`, inklusive der Projektion, die die Members-Screens in
Task 9 brauchen. Im Domain-Crate wird `my_lists` dafür zu `my_aggregates(kind)`
mit Kind-Filter; die `GET /lists`-Antwort ändert sich nicht.
`fetchAggregates()` im Frontend ruft beide Endpunkte und taggt die IDs mit
ihrem Kind.

**Cursor- und Outbox-Schlüssel werden kind-qualifiziert** — dasselbe Format wie
der Partition-Key (`LIST#{id}`, `RECIPE#{id}`) oder `{ kind, id }`, Hauptsache
eindeutig und überall gleich. Kein Altbestand, keine Migration (siehe
Greenfield-Freigabe oben) — das Format wird einfach umgestellt.

**Betroffene Testdateien:**

- `apps/mobile/test/app/sync/receive/catchUp.test.ts`
- `apps/mobile/test/app/sync/receive/fetchEvents.test.ts`
- `apps/mobile/test/app/sync/syncEngine.test.ts`
- `apps/mobile/test/app/sync/syncEngine.cycle.test.ts`
- `apps/mobile/test/app/sync/syncEngine.stop.test.ts`
- `services/adapters/src/dynamodb_membership.rs` — Test von `distinct_lists`.
  ⚠️ Dieser Test ändert als **einziger seine Aussage**: Heute sichert er zu,
  dass `RECIPE#`-Partitionen verworfen werden; künftig, dass sie **mit Kind
  geliefert** werden. Das ist die gewollte Verhaltensänderung dieses Umbaus
  und von der Freigabe oben gedeckt.

⚠️ Die Sync-Tests sind die **empfindlichsten im Repo** — sie sichern
Konvergenz, Ack/Dedup und Zyklus-Verhalten. Beim Umbau darf sich ausschließlich
die *Form* der Aggregat-Identität ändern, nie die geprüfte Zusage. Nach dem
Umbau muss die vollständige Suite grün sein, bevor irgendetwas committet wird.

### Was das für die Reihenfolge heißt

Die Generalisierung ist **Vorarbeit**, kein Nebenprodukt der Rezepte. Sie steht

Fehler darin ist nicht mit Rezept-Code vermischt. Nach Task B ist das Teilen für
Listen, Rezepte **und den kommenden Wochenplan** fertig.

## Global Constraints

- Kommentare im Code **immer Englisch** (root CLAUDE.md).
- Kein `any`, kein `as`, `const` statt `let`, `readonly` Props, `type` statt `interface`.
- Reducer replay-pur: kein `Date.now()`/`randomUUID()` im Reducer.
- **Bestehende Tests niemals ändern** ohne Freigabe — siehe Entscheidung A und B.
- Nach Backend-Änderungen: `cargo test` (in `services/`) **und** `pnpm test` + `pnpm cdk synth --quiet` (in `apps/infrastructure/`).
- Frontend-Verifikation: `pnpm exec tsc --noEmit && pnpm exec vitest run` in `apps/mobile/`.
- **Kein URL-Import in diesem Plan.** Der ist Klasse 2 mit SSRF-Fläche (`events.md:199`) und bekommt einen eigenen Plan.

### Die Sync-Engine wird gelesen, nicht überflogen

Task B fasst die **Sync-Engine** an — das Herzstück der App. Sie entscheidet
über Konvergenz, Offline-Fähigkeit und Datenverlust, und sie wird noch oft
gelesen werden. Für die dort geänderten Dateien gilt eine höhere Latte als für
Feature-Code, nach `architecture/design-principals.md` §8 (Intention-Revealing
Code) und `architecture/react-best-practices.md` (TypeScript-Patterns).

**Der Code soll sich wie eine kleine Fachsprache lesen.** Wer die Datei öffnet,
soll den Ablauf verstehen, ohne in Implementierungen abzutauchen:

```ts
// Der Zielzustand: die Absicht steht da, nicht die Mechanik
const aggregates = await deps.fetchAggregates()
for (const aggregate of aggregates) {
  const incoming = await eventsSinceCursor(deps, aggregate)
  if (isEmpty(incoming)) continue
  foldIntoConfirmedTree(deps, incoming)
  await advanceCursorPast(deps, aggregate, incoming)
}
```

**Verbindlich für die in Task B geänderten Dateien:**

- **Namen nennen die Absicht, nicht die Mechanik.** `eventsSinceCursor` statt
  `getData`, `aggregate.kind` statt `type2`, `advanceCursorPast` statt
  `updateLedger`. Vor dem Commit jeden neu eingeführten Namen einmal prüfen:
  Verrät er, *warum* es ihn gibt — oder nur, *was* er technisch tut?
- **Der Aggregat-Typ heißt überall gleich.** Nicht mal `kind`, mal `type`, mal
  `aggregateType`. Ein Begriff, ein Wort, im ganzen Repo — auch über die
  Sprachgrenze zwischen Rust und TypeScript hinweg.
- **Kurze Funktionen mit einer Aufgabe.** Passt eine Funktion nicht auf einen
  Bildschirm, tut sie zu viel und wird in benannte Schritte zerlegt. Dasselbe
  gilt für die `SyncEngine`-Klasse: wächst sie beim Umbau, werden Teile
  herausgezogen statt Methoden verlängert.
- **Keine Sammelbegriffe als Dateinamen** — kein `helpers`, `utils`, `misc`.
  Jedes Konzept bekommt einen eigenen, fachlichen Namen.
- **Kein `any`, kein `as`**, `readonly` auf allem, `const` statt `let` — die
  Regeln gelten hier ohne Ausnahme.
- **Kommentare erklären das Warum.** Die vorhandenen Kommentare in `catchUp.ts`
  und `withSync.ts` sind wertvoll (sie begründen Reihenfolgen und Invarianten)
  und müssen beim Umbau **mitwandern**, nicht wegfallen.

**Abnahme:** Nach Task B liest ein Reviewer die geänderten Dateien und kommt zu
dem Urteil, dass die Lesbarkeit **sehr gut** ist — der Ablauf ist ohne
Rückfragen nachvollziehbar. Ist das nicht der Fall, ist Task B nicht fertig,
auch wenn alle Tests grün sind. Der Umbau ist ausdrücklich auch eine Gelegenheit,
die Engine lesbarer zu hinterlassen, als sie vorher war.

⚠️ **Lesbarkeit rechtfertigt keine Verhaltensänderung.** Wenn beim Aufräumen
eine Vereinfachung verlockt, die eine Zusage verschiebt: stoppen und nachfragen.
Die Sync-Tests sichern Konvergenz, Ack/Dedup und Zyklus-Verhalten — sie sind das
Netz, nicht das Hindernis.

### Tests prüfen Fachlichkeit, nicht Implementierung

**Ein Test beschreibt eine fachliche Zusage, kein Innenleben.** Er soll noch
grün sein, wenn die Umsetzung dahinter komplett ausgetauscht wird — und rot,
sobald sich das fachliche Verhalten ändert. Ein Test, der bei einem reinen
Refactoring bricht, hat das Falsche geprüft.

**So sieht das konkret aus:**

- **Über die öffentliche Schnittstelle gehen.** Actions rein über die Action
  Creator, Ergebnisse raus über die Selektoren. Nicht in die State-Form greifen,
  keine internen Hilfsfunktionen direkt aufrufen. Genauso im Backend: Use Case
  aufrufen, Ergebnis über die Ports beobachten — nicht die In-Memory-Struktur
  inspizieren.
- **Testnamen sind Sätze über die Fachlichkeit.** `an_expired_token_is_rejected`
  statt `test_check_expiry_returns_false`. Wer den Namen liest, versteht die
  Regel, ohne den Code zu öffnen.
- **Keine Mock-Verifikation als Selbstzweck.** Nicht prüfen, *dass* eine Methode
  aufgerufen wurde, sondern *was dabei herauskommt*. Die In-Memory-Ports in
  `domain/src/memory.rs` sind echte kleine Implementierungen, genau damit man
  das Ergebnis prüfen kann statt der Aufrufe.
- **Keine Zahlen und Strings doppeln, die anderswo definiert sind.** Tests
  rechnen mit `MAX_LIST_MEMBERS`, nicht mit `6` — sonst bricht eine
  Produktentscheidung zwanzig Testerwartungen.
- **Kein Test auf CSS-Klassen, DOM-Struktur oder Reihenfolge von Aufrufen**,
  solange die Fachlichkeit das nicht vorgibt.

**Beispiele aus diesem Plan:**

| Statt (Implementierung) | Besser (Fachlichkeit) |
|---|---|
| „`scaleIngredients` multipliziert jedes `quantity`-Feld" | „Ein Rezept für 4 zeigt bei 8 Portionen die doppelten Mengen" |
| „`recipeDeleted` ruft `filter` auf dem Array" | „Ein gelöschtes Rezept taucht in der Sammlung nicht mehr auf" |
| „`create_recipe` schreibt in den EventStore" | „Der Ersteller wird Owner und kann danach einladen" |
| „Der Slice hat nach dem Fold 3 Einträge" | „Zweimal dasselbe `recipeCreated` erzeugt kein zweites Rezept" |

Wenn ein fachliches Verhalten sich nur durch Innenleben prüfen lässt, ist das
ein Hinweis auf einen fehlenden Selektor oder eine fehlende Port-Methode — nicht
die Erlaubnis, doch ins Innere zu greifen.

## Datenmodell-Klärung vorab

Die Mockups zeigen pro Rezept **Emoji, Farbe und Zeitangabe** („30 Min"), das Event-Schema in `events.md:201` kennt nur `name`, `portions`, `ingredients`, `instructions`.

Entscheidung für diesen Plan, analog zu Listen:

- **Emoji und Farbe** sind lokale Präferenzen (`preferences`-Slice, nie gesynct) — genau wie bei Listen
- **Zubereitungszeit** ist Domänendaten und kommt als optionales `durationMinutes` ins Schema
- **Zubereitung** ist im Mockup eine Schritt-Liste, im Schema ein `instructions`-String → Schema wird auf `steps: string[]` geändert, bevor es erstmalig benutzt wird (kein Bestandsdatenproblem, es gibt noch keine Rezepte)

## Bekannte Grenzen, im Review zu bestätigen

1. **Portions-Umrechnung ist reine Anzeige** — das Rezept selbst bleibt bei seinen gespeicherten Portionen.
2. **Nicht-numerische Mengen** („etwas", „1 Prise") werden beim Skalieren unverändert durchgereicht.
3. **Kein Bild pro Rezept** — die Mockups nutzen Emoji, das reicht für die erste Scheibe.
4. **`recipeUpdated` trägt das ganze Formular** — bearbeiten zwei Mitglieder dasselbe Rezept gleichzeitig, gewinnt die spätere Log-Position komplett (Membership ist davon ausgenommen, sie reist in eigenen Events). Feinere Intention-Events (`recipeRenamed`, `ingredientAdded` …) erst, wenn gleichzeitiges Bearbeiten real vorkommt.
5. **Join-Route bleibt `POST /lists/join` für alle Aggregate** — der Kind steckt im Token, nicht im Pfad. Eine generische `/join`-Route wäre hübscher, lohnt aber keinen eigenen Umbau.
